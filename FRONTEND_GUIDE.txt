  PART 1 — HOW THE APPLICATION IS STRUCTURED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is a desktop application, not a website. It runs as a native Windows app
using Electron. Inside Electron, an Angular web app is loaded in a browser
window. A small local Express server (bundled with the app) acts as a bridge
between the Angular frontend and the outside world.

  ┌──────────────────────────────────────────────────────────────────────┐
  │  ELECTRON SHELL (native OS window)                                   │
  │                                                                      │
  │  ┌────────────────────────────────────────────────────────────────┐  │
  │  │  ANGULAR 21 APP  (rendered inside Electron BrowserWindow)     │  │
  │  │                                                                │  │
  │  │  Components → Services → HttpClient → backend API             │  │
  │  └────────────────────────────────────────────────────────────────┘  │
  │                                                                      │
  │  ┌────────────────────────────────────────────────────────────────┐  │
  │  │  LOCAL EXPRESS SERVER  (localhost:3000)                        │  │
  │  │  Bundled with the app, starts in background when app opens.   │  │
  │  │  Currently has only a /api/health endpoint.                   │  │
  │  │  Will proxy or host scan-related local logic in future.       │  │
  │  └────────────────────────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────────────────────────┘
            │ HTTP calls
            ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │  NET-SCAN-BACKEND  (separate Node.js service, can be remote)         │
  │  Exposes: /api/v1/scanner/methods, ping, test-connection,            │
  │           hardware, software, scan                                   │
  └──────────────────────────────────────────────────────────────────────┘

THREE PROCESSES RUN WHEN THE APP STARTS (dev mode):
  1. ng serve     → Angular dev server on port 4200
  2. tsx server/  → Local Express server on port 3000
  3. electron .   → Electron window (waits for both servers to be ready first)

In production (packaged .exe), Electron bundles the Angular build as static
files and spawns the Express server as a Node.js child process internally.

  PART 2 — ROUTING STRUCTURE (All Pages and Their Paths)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The router uses hash-based navigation (#/) so it works inside Electron's
file:// URL without a server-side router.

  /  (root)
  └── redirects to /auth/sign-in

  /auth                          Layout: AuthenticationLayout
  ├── /auth/sign-in              Page: SignInPage
  └── /auth/sign-up              Page: SignUpPage

  /dashboard                     Layout: DashboardLayout  (sidebar + topbar)
  ├── /dashboard/home            Page: HomePage
  ├── /dashboard/assets          Page: AssetsPage
  ├── /dashboard/reports         Page: ReportsPage
  ├── /dashboard/software        Page: SoftwarePage
  ├── /dashboard/scanning        Page: ScanningPage
  └── /dashboard/configuration   Page: ConfigurationPage

  /application
  └── /application/error/404     Page: ErrorPage

  ** (anything else)             redirects to /application/error/404

All dashboard routes use lazy loading — the component code is only downloaded
from the bundle when the user navigates to that route. This keeps initial
load time fast.

────────────────────────────────────────────────────────────────────────────────
  SignInPage
  Route: /auth/sign-in
  File: src/app/pages/Authentication/sign-in-page/
────────────────────────────────────────────────────────────────────────────────

  PURPOSE:
    The entry point to the application. User enters credentials to log in.
    On success, navigate to /dashboard/home. On failure, show error toast.

  COMPONENTS ON THIS PAGE:
    - Email input field (Angular Material MatFormField + MatInput)
    - Password input field with show/hide toggle
    - "Sign In" button
    - "Don't have an account? Sign Up" link → /auth/sign-up
    - Error message display area

  FORM FIELDS:
    email    : required, must be valid email format
    password : required, minimum 6 characters

  BACKEND INTEGRATION:
    Currently this app does not have its own auth backend — authentication
    needs to be added. The integration plan:

    When the user clicks Sign In:
      1. Validate the form locally (Angular Reactive Forms)
      2. Call POST to your auth endpoint with { email, password }
      3. Receive back an access token (JWT)
      4. Store the token in localStorage or a secure cookie
      5. Navigate to /dashboard/home

    Note: the scan backend (net-scan-backend) does not have user auth —
    it is a service-to-service tool. You need a separate auth service or
    add user management to the backend.

  GUARD:
    This page should use a GuestGuard — if the user is already logged in
    (token exists in storage), redirect directly to /dashboard/home
    so they don't see the login page unnecessarily.

────────────────────────────────────────────────────────────────────────────────
  SignUpPage
  Route: /auth/sign-up
  File: src/app/pages/Authentication/sign-up-page/
────────────────────────────────────────────────────────────────────────────────

  PURPOSE:
    New user registration. On success, either auto-login or redirect to sign-in.

  COMPONENTS ON THIS PAGE:
    - Full name input
    - Email input
    - Password input
    - Confirm password input
    - "Create Account" button
    - "Already have an account? Sign In" link

  FORM VALIDATION:
    - All fields required
    - Email must be valid format
    - Password minimum 8 characters
    - Confirm password must match password

  BACKEND INTEGRATION:

  │  IP Address  | Status | Hostname | OS | CPU | RAM | Method | Time      │
  │  192.168.1.1 | ✓ Done | SERVER01 | W11| ... | 16GB| PS     | 45s       │
  │  192.168.1.2 | ✗ Fail | —        | —  | —   | —   | PS     | Ping fail │
  │  192.168.1.3 | ⟳ Running ...                                          │
  └──────────────────────────────────────────────────────────────────────────┘

  BACKEND INTEGRATION — STEP BY STEP:

  STEP 1: Load Available Methods (on page load)
  ──────────────────────────────────────────────
  Call: GET /api/v1/scanner/methods
  Purpose: Populate the method dropdown with names and requirement descriptions.
  Response: Array of { id, name, description, requirements, linuxCompatible }
  When received: Show each method as a dropdown option. When the user selects
    a method, show the "requirements" text below the dropdown as a helper note
    so they know what ports/features are needed on the target.

  STEP 2: Test Connection (optional, before starting scan)
  ─────────────────────────────────────────────────────────
  Triggered by: "Test Connection" button
  Call: POST /api/v1/scanner/test-connection
  Body:
    {
      "target": "192.168.1.10",
      "method": "powershell",
      "credentials": {
        "username": "admin",
        "password": "password123",
        "domain": "CORP"
      }
    }
  Response success: { success: true, target: "...", method: "..." }
  Response failure: { success: false, error: "WinRM port 5985 not reachable" }
  UI: Show a green checkmark or red X next to the Test Connection button.
    If failed, show the error reason so the user knows whether it is a
    network issue (port blocked) or credentials issue (auth failed).

  STEP 3: Validate Each IP in the List
  ──────────────────────────────────────
  Before sending to backend: split the textarea by newlines and commas,
  strip whitespace, filter empty lines. Validate each entry against the
  same rules as the backend (IPv4 format or valid hostname). Mark invalid
  entries in red before the scan starts so the user can fix them.
  This saves API round-trips for obviously bad input.

  STEP 4: Ping Each IP (optional pre-flight)
  ──────────────────────────────────────────
  If you want to show which IPs are alive before running a full scan:
  Call: POST /api/v1/scanner/ping  for each IP
  Body: { "target": "192.168.1.10" }
  Response: { alive: true/false, latency: 12 }
  UI: Show alive/dead indicator in the results table while the full scan
    is queued/running.

  STEP 5: Run Full Scan for Each IP
  ───────────────────────────────────
  For each IP in the list, call POST /api/v1/scanner/scan
  Body:
    {
      "target": "192.168.1.10",
      "method": "powershell",
      "credentials": {
        "username": "admin",
        "password": "password123",
        "domain": "CORP"
      },
      "skipPing": false,
      "skipSoftware": false,
      "continueOnError": true
    }

  Response shape on success:
    {
      "success": true,
      "data": {
        "target": "192.168.1.10",
        "method": "powershell",
        "pingSuccess": true,
        "connectionSuccess": true,
        "hardware": { "Hostname": "SERVER01", "Cpu": "Intel...", ... },
        "software": [ { "ApplicationName": "Chrome", ... }, ... ],
        "errors": {},
        "startedAt": "2026-04-22T10:00:00Z",
        "completedAt": "2026-04-22T10:01:15Z"
      }
    }

  Response shape on partial failure (continueOnError=true):
    {
      "success": true,
      "message": "Scan completed with some errors",
      "data": {
        "pingSuccess": true,
        "connectionSuccess": true,
        "hardware": { ... },
        "software": null,
        "errors": { "software": "Registry query timed out" }
      }
    }

  STEP 6: Control Concurrency (for multiple IPs)
  ────────────────────────────────────────────────
  Do NOT fire all 1000 HTTP requests at once. Use a concurrency limiter
  in the frontend service so that only N scans are in-flight at any time.
  Recommended N: 10-20 for a desktop app (the backend handles the rest).

  Implementation pattern:
    - Maintain a queue of pending IPs
    - Maintain a count of active (in-flight) requests
    - When a scan completes, pull the next IP from the queue and start it
    - Update the progress bar after each completion

  STEP 7: Display Results as They Come In
  ─────────────────────────────────────────
  Do not wait for all scans to finish before showing results. As each
  scan call returns, update that row in the results table immediately.
  The user sees live progress: rows flipping from "Running" to "Done" or
  "Failed" one by one.

  STEP 8: Save Results to Local Storage / Export
  ────────────────────────────────────────────────
  After each scan result arrives, save it to localStorage or IndexedDB
  so AssetsPage and SoftwarePage can display the collected data.
  Offer a "Export CSV" button that formats the hardware results using the
  CSV-style field aliases already in the hardware response
  (HostName, Operating_System, CPU, TotalPhysicalMemory (GB), etc.).

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Services are Angular singleton classes injected into components. They hold
the logic for all HTTP calls and keep components clean.

────────────────────────────────────────────────────────────────────────────────
  ScannerService
  File: src/app/services/scanner.service.ts  (to be created)
  Used by: ScanningPage, HomePage (quick scan), AssetsPage (re-scan)
────────────────────────────────────────────────────────────────────────────────

  This is the central service for all scan backend calls.

  PROPERTIES:
    baseUrl       : string  — read from ConfigurationService (default: http://localhost:3000/api/v1)
    activeMethods : Signal<MethodInfo[]>  — cached list from GET /methods

  METHODS:

  getMethods()
  ─────────────
  CALLS: GET /api/v1/scanner/methods
  RETURNS: Observable<MethodInfo[]>
  WHEN: Called on ScanningPage init and ConfigurationPage Test Connection.
  HOW: Makes HTTP GET. On success, caches result in a signal so components
    don't need to call it on every load.

  ping(target: string)
  ─────────────────────
  CALLS: POST /api/v1/scanner/ping
  BODY: { target }
  RETURNS: Observable<PingResult>  — { alive, target, latencyMs }
  WHEN: Called by ScanningPage if user wants to pre-check alive status,
    or by HomePage quick scan pre-flight.

  testConnection(target, method, credentials)
  ─────────────────────────────────────────────
  CALLS: POST /api/v1/scanner/test-connection
  BODY: { target, method, credentials: { username, password, domain? } }
  RETURNS: Observable<ConnectionTestResult>  — { success, error? }
  WHEN: Called when user clicks "Test Connection" button.

  fetchHardware(target, method, credentials)
  ───────────────────────────────────────────
  CALLS: POST /api/v1/scanner/hardware
  BODY: { target, method, credentials }
  RETURNS: Observable<HardwareInfo>
  WHEN: Called by AssetsPage "Hardware Refresh" button for a single machine.

  fetchSoftware(target, method, credentials)
  ───────────────────────────────────────────
  CALLS: POST /api/v1/scanner/software
  BODY: { target, method, credentials }
  RETURNS: Observable<{ hostname, count, software: SoftwareEntry[] }>
  WHEN: Called by SoftwarePage "Software Refresh" for a single machine.

  fullScan(options: FullScanOptions)
  ────────────────────────────────────
  CALLS: POST /api/v1/scanner/scan
  BODY:
    {
      target: string,
      method: string,
      credentials: { username, password, domain? },
      skipPing: boolean,
      skipSoftware: boolean,
      continueOnError: boolean
    }
  RETURNS: Observable<ScanResult>
  WHEN: Called by ScanningPage for each IP in the scan list.

  scanMultiple(ips, method, credentials, options, concurrency = 10)
  ──────────────────────────────────────────────────────────────────
  NOT a direct backend call — this is a frontend orchestration method.
  HOW IT WORKS:
    Maintains a queue of IPs. Starts `concurrency` number of fullScan()
    calls simultaneously. As each one finishes, it pulls the next IP from
    the queue and starts a new scan. Emits progress events (completed count,
    failed count, each result as it arrives) as an Observable so the
    ScanningPage can update the UI in real time.
  WHEN: Called by ScanningPage "Start Scan" button when multiple IPs are entered.

  PART 12 — SCANNING FLOW (Full End-to-End from UI to Backend and Back)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is the complete flow when a user enters 500 IPs and clicks "Start Scan":

  USER ACTIONS
  ─────────────
  1. User types or pastes IPs into the textarea (or uploads a file)
  2. IpInputComponent validates each IP in real time — red highlight = invalid
  3. User selects method from MethodSelectorComponent dropdown
  4. User enters credentials in CredentialFormComponent
     (or selects a saved preset from ConfigurationService)
  5. User optionally clicks "Test Connection" → shows ✓ or ✗ result
  6. User clicks "Start Scan"

  FRONTEND PROCESSING
  ─────────────────────
  7. ScanningPage collects valid IP list, method, credentials, options
  8. Calls ScannerService.scanMultiple(ips, method, credentials, options, concurrency=10)
  9. scanMultiple() initializes a queue of 500 IPs and starts 10 concurrent scans

  CONCURRENT SCAN EXECUTION (per IP)
  ─────────────────────────────────────
  10. ScannerService.fullScan({ target: "192.168.1.1", method, credentials, ... })
  11. Angular HttpClient sends POST /api/v1/scanner/scan to the backend
  12. AuthInterceptor adds Bearer token to the request header
  13. Request arrives at net-scan-backend

  BACKEND PROCESSING
  ───────────────────
  14. Rate limit check → allowed
  15. Zod schema validates: IP format, method enum, credentials present
  16. Request ID (UUID) and startTime attached
  17. ScannerService.fullScan() starts:
      a. pingHost("192.168.1.1")  → spawn OS ping → alive: true, 12ms latency
      b. getMethod("powershell").testConnection() → TCP check port 5985 → open
         → run tiny PS script → hostname returned → connection: success
      c. getMethod("powershell").fetchHardwareInfo() → write temp .ps1 file
         → spawn powershell.exe -File → WMI queries run on target
         → JSON returned → temp file deleted
         → normalizeHardware() flattens field names
      d. getMethod("powershell").fetchSoftwareInfo() → write temp .ps1 file
         → registry query on target → JSON array returned → temp file deleted
         → normalizeSoftware() adds timestamps and aliases
  18. Response built: { success: true, data: { hardware, software, ... }, meta }
  19. HTTP 200 sent back

  FRONTEND RECEIVES RESULT
  ─────────────────────────
  20. Observable emits the ScanResult for that IP
  21. ScannerService.scanMultiple() emits a progress event
  22. ScanningPage receives the event, updates the results table row:
      192.168.1.1 → Status: ✓ Done | Hostname: SERVER01 | OS: Win11 | ...
  23. ScanStoreService.addResult(result) → stored in memory + localStorage
